# rust-filc

This crate is a crude proof-of-concept of an interaction layer between [Fil-C](https://fil-c.org/) code and Rust, without C ("Yolo-C") FFI.

The core idea is that since Rust's only supported foreign-language FFI is C ABI, which we cannot really use without losing Fil-C's security guarantees, rust-filc launches Fil-C code in a separate process and communicates with it through binary RPC. This is less performant than ordinary FFI, but lets us not use C ABI.

This crate is experimental and is not an official part of the Fil-C project. It was tested on x86-64 Linux with Rust 1.85 and Fil-C 0.683.

## Quickstart

Add these two dependencies:

```toml
[dependencies]
filc = "0.1"

[build-dependencies]
filc-build = "0.1"
```

Declare interface of your Fil-C program in a Rust module:

```rust
// src/legacy.rs

#[filc::bridge(
    name = "legacy",
    header = "legacy.h",
    sources = ["legacy.c"],
    includes = ["."],
)]
unsafe extern "Fil-C" {
    pub fn add(left: i32, right: i32) -> i32;

    #[filc::free("release_greeting")]
    pub fn greet(name: &str) -> String;

    pub fn counter_new(initial: i64) -> *mut counter_t;
    pub fn counter_add(counter: *mut counter_t, delta: i64) -> i64;

    #[filc::drop]
    pub fn counter_drop(counter: *mut counter_t);
}
```

The corresponding C header includes `extern_filc.h`, which is generated by
`filc-build` and added to the helper compiler's include path:

```c
// legacy.h

#ifndef LEGACY_H
#define LEGACY_H

#include "extern_filc.h"

#include <stdint.h>

typedef struct counter counter_t;

int32_t add(int32_t left, int32_t right);

extern_filc_string greet(extern_filc_string name);
void release_greeting(const char *result);

counter_t *counter_new(int64_t initial);
int64_t counter_add(counter_t *counter, int64_t delta);
void counter_drop(counter_t *counter);

#endif
```

`extern_filc_string` is a pointer-length pair, not a null-terminated C string.
An existing API that takes or returns `char *` therefore needs a small C
adapter that supplies the length. The implementation can otherwise use the
generated type like any other C structure:

```c
// legacy.c

#include "legacy.h"

#include <stdlib.h>
#include <string.h>

struct counter {
    int64_t value;
};

int32_t add(int32_t left, int32_t right) {
    return left + right;
}

extern_filc_string greet(extern_filc_string name) {
    static const char prefix[] = "hello, ";
    size_t prefix_len = sizeof(prefix) - 1;

    if (name.len > SIZE_MAX - prefix_len) {
        return (extern_filc_string){0};
    }

    size_t result_len = prefix_len + name.len;
    char *result = malloc(result_len);
    if (result == NULL) {
        return (extern_filc_string){0};
    }

    memcpy(result, prefix, prefix_len);
    if (name.len != 0) {
        memcpy(result + prefix_len, name.ptr, name.len);
    }

    return (extern_filc_string){.ptr = result, .len = result_len};
}

void release_greeting(const char *result) {
    free((void *)result);
}

counter_t *counter_new(int64_t initial) {
    counter_t *counter = malloc(sizeof(*counter));
    if (counter != NULL) {
        counter->value = initial;
    }
    return counter;
}

int64_t counter_add(counter_t *counter, int64_t delta) {
    counter->value += delta;
    return counter->value;
}

void counter_drop(counter_t *counter) {
    free(counter);
}
```

Connect the module to where you want to call it:

```rust
// src/lib.rs

pub mod legacy;
```

And declare the module for the compiler in `build.rs`:

```rust
fn main() {
    filc_build::build("src/legacy.rs")
        .expect("failed to build the Fil-C helper");
}
```

After that, you can call generated Fil-C functions without `unsafe`:

```rust
let answer = legacy::add(20, 22)?;

let counter = legacy::counter_new(10)?;
assert_eq!(legacy::counter_add(&counter, 5)?, 15);
```

### What and why

`unsafe` is only used in interface declaration. You must verify that your Rust signatures are equivalent to Fil-C's ones. Then, generated functions are used with normal, safe Rust types.

Currently, you can pass:

- numeric types and `bool`;
- strings in UTF-8;
- byte slices;
- opaque C-objects through remote handles.

Strings and bytes are always copied. No C pointer address or Fil-C capability cross the process boundary.

For instance, returned `*mut counter_t` is transformed into Rust `CounterT`. Inside it, there's an object identifier in Fil-C's process. This handle is impossible to accidentally use after helper process's restart or pass to another connection.

Fil-C does not encode ownership in signatures, so you must define memory release explicitly.

`#[filc::free("release_greeting")]` tells the generator to copy returned data to Rust and then use the declared release function.

`#[filc::drop]` marks the destructor of an opaque object. For this object, the generator automatically builds `Drop` and an explicit consuming function:

```rust
legacy::counter_drop(counter)?;
```

Helper process is launched on first call and then reused. If Fil-C detects a memory error and terminates the process, current handles become invalid. Old handles cannot be used after restart, so next call launches a new helper.

Of course, the process is not a full sandbox. Fil-C protects against memory errors but not logic errors or malicious code. Helper process inherits parent's rights on files, network, etc.

## Why use separate process

Fil-C is compatible with C source code, but not C ABI. Rust cannot natively call Fil-C ABI, while building a C-ABI-based adapter would bring us back to unsafe pointers.

So, `filc` keeps two separate environments:
- The main program is still a normal Rust program;
- The helper and its whole dependency closure are built with Fil-C;
- Between processes, only copied values are passed.

It follows that `extern "Fil-C"` is implemented through an attribute macro. Without one, Rust compiler would obviously reject this syntax.

## Fil-C compiler

You have to declare the path to your Fil-C compiler using `FILC_CC`:

```console
FILC_CC=/path/to/fil-c/build/bin/clang cargo build
```

If the compiler is not found, compilation fails.

This repo uses Nix for pinning Fil-C and a reproducible dev environment. You don't have to use Nix to use rust-filc.

Due to the env var requirement, rust-analyzer normally fallbacks to not actually building the helper process. `cargo build` and `cargo check` still require the compiler.

## 0.1.0 limitations

Currently, rust-filc only supports synchronous calls, scalar types, copied strings and bytes, and opaque handles.

Not supported (but planned):

- shared memory;
- passing real pointers;
- callbacks;
- variadic functions;
- C++ exceptions;
- streaming of large values.

0.1.0 is rather just a proof-of-concept that is technically absolutely possible to use for a lot of projects if you're willing to mess around with it for a while. If you do, feel free to submit PRs for whatever you believe will improve rust-filc's UX.
